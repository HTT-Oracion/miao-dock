# ver3.0 设计稿 ↔ 产品实现 · 差异比对清单

> 本文件是「全模块逐项比对」的执行台账：**每一行都带取证方式**，不写"看起来一致"。
> 设计输入：`miao-dock-design/refactor_ver3.0/`（`index.html` + `js/*.js` + `styles.css`）。
> 兜底依据：`miao-dock` 现有实现。**番剧模块不在本表范围**（零改动红线）。

## 0. 取证方式（可复现，不靠肉眼）

| 手段 | 做什么 | 为什么不能只靠它 |
|---|---|---|
| 文案抽取比对 | 从设计稿 HTML/JS 里抽所有含中日文的字面量，逐条查产品 `src/**` | 设计稿里的示例数据（歌名 / 漫画台词 / 演示面板）不该出现在产品里，必须人工分流 |
| class 结构扫描 | 设计稿用到的 class 逐条查产品源码 | 两侧命名体系不同（`.snav` ↔ `.set-nav-item`），同名才算缺失会大量误报 |
| **界面文本转储** | 用 CDP 打开设计稿与产品，各取一次 `body.innerText` 行集合，做差集 | 只能证明"文案在不在"，证明不了间距与动效 |
| **交互探针** | 用 CDP 真敲键、真点击，读回 DOM（命中数 / 高亮类 / 分组切换） | 只能覆盖被写成断言的那几条路径 |

本轮用的三个脚本（一次性探索件，留在 `.tmp/ver3-audit/`，未登记进 `e2e/`）：

```
node .tmp/ver3-audit/extract-strings.mjs                 # 设计稿文案 → 产品源码命中率
node .tmp/ver3-audit/structure-scan.mjs settings         # 设计稿 class → 产品源码
node .tmp/ver3-audit/dump-text.mjs <url> <out.json> [点击选择器…]   # 界面文本转储
node .tmp/ver3-audit/probe-settings-search.mjs           # 设置搜索交互探针
```

> ⚠️ **已知的瞬时假红（2026-10-22 实测一次）**：`npm run check` 与 `git commit` **同一条命令**里连着跑时，
> `engine-download-entry` 的 E2（读 `src/components/Sidebar.tsx`）可能红一次，紧接着单跑与再跑全绿。
> 原因是 lint-staged 提交后要把暂存前的备份**还原回工作区**，那一瞬间该文件处于中间态。
> 判据：**红在"读某个源文件"的那一条**、且单跑即绿 ⇒ 先怀疑提交流水线，别急着改代码；
> 但也不能当成"偶发忽略" —— 复跑两次仍红就必须查。

> ⚠️ 本机 **没有可用的截图能力**（无 Playwright，`e2e/capture.mjs` 是 macOS 专用，
> 且当前模型不能读图）。因此"像素级"只能靠**设计稿 CSS 数值 ↔ 产品 SCSS 数值**逐条对，
> 不能靠看截图。这一点必须写在这里，否则下一个人会以为已经"看过了"。

## 1. 全局框架（壳层）

### 1.1 动效与配色（第五轮系统核对）

**动效令牌本身是对齐的**：`--miao-dur-fast/base/slow` = 140/240/380ms，
`--miao-ease-spring` = `cubic-bezier(.22,1.3,.36,1)`、`-spring-soft` = `(.34,1.4,.64,1)`、
`-out` = `(.16,1,.3,1)`，与设计稿逐字一致。问题出在**没用令牌**的地方：

| 位置 | 改前 | 设计稿 | 处置 |
|---|---|---|---|
| `.music-lyr-line` | `transition: all 0.2s` | 行本身无过渡，只有逐字 `color .12s linear` | ✅ 收敛为 `color/opacity var(--dur-fast) linear`（`all` 会把 font-size +3px 也做成动画 ⇒ 居中歌词"整行慢慢长大"，D-137 的根因） |
| `.di-capsule`（灵动岛） | 形变 320ms + `cubic-bezier(.22,.61,.36,1)`；淡入淡出 260ms + Material 曲线 | 形变 **380ms + `--ease-spring`**（会轻微过冲）；padding/background 240ms | ✅ 改 380ms 弹簧 + 240ms `--ease-out`；`DynamicIsland` 的 `MORPH_MS`/`FADE_MS` 同步 380/240（`ISLAND.morphDurationSync` 双向钉） |
| `.di-bar i` 进度填充 | `width 0.2s` | `.rail-fill` = `width .16s linear` | ✅ 160ms linear |
| 灵动岛波形 / 样式卡 | `opacity 0.18s` / `background 0.2s ease` | `--dur-fast` | ✅ 改令牌 |
| `.ui-range` 滑块拇指 | `transform 0.12s` | `.rail-thumb` = `transform var(--dur-fast) var(--ease-out)` | ✅ 改令牌 |
| `.switch-track` | `background 0.15s` | `background/border-color var(--dur-base)` | ✅ 改令牌 |
| `.set-cache-item` 悬停 | `background 0.15s` | 行悬停 `--dur-fast` | ✅ 改令牌 |
| **`.ui-cbtn`（图标按钮）** | 30×30 / 圆角 8 / **无按下反馈** | `.icon-btn`：34×34 / 圆角 10 / `:active scale(.94)` | ✅ 几何 + 按下反馈 + 位移走 `--ease-out` |
| **`.ui-cbtn.main`（播放/暂停）** | **主题粉色实心** 32×32 | `.pb-play`：**墨色实心** 36×36 / `:active scale(.95)` | ✅ 改墨色 + 36 圆形 + 按下 .95 |
| **`.ui-cbtn.is-on`** | 粉色 | `.icon-btn.is-on`：主色 ink + 主色淡底 | ✅ 改语义色 |
| 其余 9 处 `--md-pink`（焦点环 / 开关开启态 / 导航高亮） | 粉色 | 设计稿明令粉不得作 UI 主色 | ✅ 全改 `--miao-primary` 系 |

> 口径：**"配色对齐"不等于"换成新色板"**。上面最后三行是上一轮"换皮式"改造的残留 ——
> 色板换成了 ver3，但**语义**还是旧的（播放键用粉色、开关开启态用粉色）。
> 设计稿的播放键是墨色实心（"最实的那一枚"），开关开启态是主色。

### 3.4 话级「归并到…」：不是键口径问题，是后端没有这个能力

第十五轮把它登记为"合并键有两种写法，怕合错对象"。本轮把链路读完，结论更硬：

- `POST /api/v1/library/{name}/merge` 的 `{name}` 是**顶层目录名**（`handlers.rs` 直接
  `library::merge_archive_dir()` + `rename` 到目标书的某话目录下）；
- 前端 `mergeTarget` 的取值也只可能是顶层目录：`useLibraryModel` 里三种 `key` 分别是
  `b.bookName` / `o.dirName` / `c.comicName`，**没有** `${book}/${chapter}` 形态
  （`reworkingComics` 里那种双形态键是"在跑任务"的判定，不是合并键）；
- 也就是说：**已经归并进某本书的话**，没有任何端点能把它再搬到另一本书里。

所以话卡菜单里那条「归并到…」**不能加** —— 加了只会得到一个 4xx。设计稿里有它，
是因为设计稿把每话都当作顶层条目（它的"归并"就是把顶层目录并进书）。
这条按"设计稿漏掉了现有功能/能力边界时以现有项目为准"处理，登记在案而不是硬编一个按钮。

### 4.4 其余平台的「今日精选」：查清后**不做**（能力边界，不是遗漏）

`newSongs` 目前只有网易云有实现（`/personalized/newsong`，匿名可取）。逐条查过另外三个适配器：

| 平台 | 现有接口 | 有没有"新歌池" |
|---|---|---|
| 酷狗 | `search` / `artist_songs` / `playlist_tracks` / `guess_like` / `get_rank_list` + `rank_songs` | ❌ 无独立新歌接口；新歌只能从**榜单**里取 |
| QQ 音乐 | `search` / `playlist_tracks` / `get_rank_list` + `get_rank_songs` / `recommend_playlists` | ❌ 同上 |
| 咪咕 | `search` / `playlist_tracks` / `rank_list` + `rank_songs` / `recommend_playlists` | ❌ 同上 |

三家的"新歌"都只能靠榜单里的**新歌榜**——而"新歌榜"这一节**已经在官方榜单区里**了。
再把它搬一份到「今日精选」，用户会看到同一批歌出现在两处，而且第二处的标题还叫"为你挑选"
（其实不是为他挑的）。所以保持 `newSongs: false`，该节在这三个平台**整块不渲染**。
真要做，得先确认各家的新歌接口与返回形状（本机离线无法验证），那是单独一轮的数据面工作。

# 字号与响应式方案建议

> **状态：建议稿（未改代码）** · 2026-10-30
> 依据：`src/styles/*.scss` 实测 570 处 `font-size` 的分布 + `base.scss` 的四档 `--ui-scale`。

---

## 一、字号偏小的实测证据

源码里 570 处 `font-size`，分布如下（构建期统一乘 `--ui-scale`）：

| 区间 | 处数 | 占比 | 主要用途 |
|---|---|---|---|
| ≤ 10px | **199** | **35%** | 徽标 / 元信息 / 表头 / 说明 |
| 9.5px 单值 | 53 | 9% | 卡片副行、路径、端口号 |
| 10px 单值 | 117 | 21% | 表头、chip、辅助文案 |
| 11–12px | 272 | 48% | 正文主力 |
| ≥ 13px | 59 | 10% | 标题 |

**问题不在"某一处太小"，而在小字号占比过高**：三分之一的可读文本落在 9.5–10px。

在 **1180 宽（默认窗口）** 下 `--ui-scale = 0.95`，于是：

- `9.5px` → 实际 **9.0px**
- `10px` → 实际 **9.5px**

Windows 默认 100% 缩放下，9px 相当于「小五号再小一档」，长时间读会累。

## 二、字号建议（按优先级）

### ① 先把「地板」抬起来：设 11px 下限

现在最小的可读文本是 8.5px（17 处，多为 `st-badge` 徽标）。建议：

| 现在 | 建议 | 说明 |
|---|---|---|
| 8.5px（徽标） | **10px** | 徽标是短词（「待译」「已完成」），放大不加宽多少 |
| 9.5px（53 处） | **10.5px** | 卡片副行、端口号 |
| 10px（117 处） | **11px** | 表头、chip、辅助文案 |
| 11px（109 处） | **11.5px** | 正文小号 |
| 12px（163 处） | 保持 | 已经是正文基准，Windows 上 12px ≈ 小四，合适 |

**效果**：`≤10px` 占比从 35% 降到 **~5%**（只留真正的角标）。

**风险**：表格与卡片会变高。队列行高 58px 需同步到 60–62px；`.chapter-card` 的 `.cc-row` 行距要复查。

### ② 把 570 处「散装字号」收敛成 6 档阶梯

现在是 29 个不同取值。建议只留：

```
--fs-micro: 10px    徽标 / 角标
--fs-xs:    11px    元信息 / 表头 / 说明
--fs-sm:    12px    正文（默认）
--fs-base:  13px    强调正文
--fs-lg:    15px    小标题
--fs-xl:    18px    区块标题
--fs-2xl:   22px    页面标题
```

**收益**：改字号是改一处，不是全仓搜。**代价**：这是个纯机械但量大的重构（570 处），建议用脚本按"最近的档"映射，再人工复核边界情况。

> ⚠️ 注意：`check:units` 与 `check:ia` 里有一批**写死 px 的断言**（如 `.text-btn` 是 11.5px、`.set-ctl-note` 是 9.5px）。改字号必须同步那些断言，否则会红 —— 而**红是对的**。

### ③ 别急着改 `--ui-scale` 的档位

有人会想"把 1.0 改成 1.1 全局放大"。**不建议**：

- 它只缩放字号、不缩放间距与圆角 ⇒ 放大后文字会挤（与设计稿同口径的取舍）。
- 它按**视口宽度**分档，而"字太小"是**屏幕 DPI** 的问题 —— 1080p 笔记本和 4K 显示器在同样窗口宽度下要的字号不同。

**更对的做法**：档位跟随 **devicePixelRatio**（见下节）。

## 三、响应式方案的问题

### 现状

两套并行的机制：

| 机制 | 位置 | 作用 |
|---|---|---|
| `--ui-scale` 四档 | `base.scss` | 按**视口宽度**缩放全部字号（1 / 0.95 / 1.06 / 1.12 / 1.18） |
| `@media (max-width: …)` | 各分片 | 改布局（`.lib` 左栏宽度三档、`.page-grid` 列数等） |

### 四个具体问题

**① 断点是"魔法数字"，散在各处**

`1360 / 1180 / 1040 / 1500 / 1720 / 1920` 分散在十几个分片里，没有一处列出全部。改一处不知道会影响谁。

**② 字号档和布局档不同源**

字号在 `1180` 降到 0.95，而布局在 `1180` 也改左栏宽度 —— 两件事恰好同值，但**没有机制保证**。哪天布局档改成 1200，字号还在 1180 降，就会出现"布局已进入窄屏、字号还没缩"的错位。

**③ 缩放与 DPI 无关**

```css
@media (min-width: 1920px) { --ui-scale: 1.18 }
```

1920 的 100% 屏和 1920 的 150% 屏（逻辑宽 1280）拿到的是**不同**档位，但用户看到的物理字号可能一样。真正决定"字看起来多小"的是 `devicePixelRatio` + 视口宽度。

**④ 窗口可自由拖动，而断点假设了固定宽度**

这是一个**桌面应用**，用户可以把窗口拖到任意宽度（780–2560）。`@media` 是全局的，无法表达"右栏自己变窄了该怎么办"。

### 建议

**① 断点集中成一组 CSS 变量 + 一份清单**

```scss
// base.scss
:root {
  --bp-sm: 1040px;
  --bp-md: 1180px;
  --bp-lg: 1360px;
  --bp-xl: 1500px;
  --bp-2xl: 1720px;
}
```

CSS 变量不能直接用于 `@media`（这是 CSS 的硬限制），所以**真正的动作是**：把断点写进 `base.scss` 的注释清单，并加一条 `check:units` 断言 —— 扫描所有分片里的 `@media (max-width: Npx)`，N 必须是清单里的值。

**收益**：任何"随手写个 1200"都会被门禁拦住。成本：一条 30 行的断言。

**② 字号档跟随"宽度 + DPI"，而不是只看宽度**

```scss
@media (min-width: 1500px) { :root { --ui-scale: 1.06 } }
@media (min-width: 1500px) and (min-resolution: 1.5dppx) { :root { --ui-scale: 1.0 } }
```

逻辑：**高 DPI 屏本来就把像素放大了**，再叠 `--ui-scale` 会过大。同理低 DPI 的大屏才需要放大。

**③ 容器查询（container query）替代一部分 `@media`**

CSS 容器查询已可用（Chromium 105+，WebView2 满足）。`@media` 问的是"窗口多宽"，而**真正该问的是"这个面板多宽"**：

```scss
.lib-right { container-type: inline-size; }
@container (max-width: 620px) {
  .chapter-grid { grid-template-columns: repeat(auto-fill, minmax(150px, 1fr)); }
}
```

**收益**：左栏变宽时右栏自己调，不需要知道窗口宽度。**代价**：`container-type` 会创建新的包含块 —— 与 `.compare { position: fixed }` 那类写法冲突（我在 D-407 踩过同源的坑），改造前要逐个确认。

**④ 优先用 `clamp()` 而不是断点**

现在 `.chapter-grid` 已经是 `minmax(clamp(162px, 11.5vw, 188px), 1fr)` —— 这是**对的方向**。同样的写法可以推广到间距、内边距，减少断点数量。

## 四、如果只做一件事

**把 9.5px / 10px 两档抬到 10.5px / 11px**（约 170 处，可用脚本按值替换）。

- 收益最大：直接消灭"三分之一文本 ≤10px"。
- 风险最小：只动两个字面值，不引入新机制。
- 需要同步：`check:units` / `check:ia` 里写死的那几个 px 断言；队列行高可能要 +2px。

其余建议（字号阶梯、容器查询、DPI 档）都是**结构性改造**，建议单独立项。

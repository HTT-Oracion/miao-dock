# 自测逻辑约束

> 本文件回答一个问题：**这次改动该不该写自测、写到什么程度**。
>
> 它约束的是**判断标准**，不是命令清单 —— 跑什么命令见
> [`commands.md`](commands.md)；断言怎么可反证见 `AGENTS.md` §2 第 1–4 条。
>
> 🔴 背景：本仓库 `e2e/` 下的脚本已近百个。数量本身不是问题，**为凑数而建的低价值脚本**才是 ——
> 它们让 `check:full` 从 30 秒变成几分钟、把真问题埋进噪声，而且长期没人看。
> 所以这里给的是"什么时候**不必**写"的许可，与"什么时候**必须**写"的底线。

---

## 1. 核心原则

- 根据改动内容、影响范围和回归风险决定验证方式，**不得机械地要求每项改动都新增自测脚本**。
- **优先复用**现有测试、检查命令和验收流程。已有测试能覆盖改动时，应更新或复用现有测试，不得无故重复建设。
- 测试的目的是**验证实际行为和降低回归风险**，而不是追求测试数量、测试文件数量或形式上的覆盖率。
- 不得将**未执行**的测试描述为已通过，也不得以构建成功代替所有必要的功能验证。

## 2. 必须编写或更新自动化测试的情况

涉及以下内容时，必须提供与改动相匹配的自动化测试；**优先更新现有测试**，只有无法合理复用时才新增测试文件或脚本。

- 核心业务逻辑、数据解析、数据转换及状态管理。
- 配置、文件及其他持久化数据的读写和校验。
- Tauri 命令、前后端通信、事件传递及模块间接口。
- 翻译引擎、模型加载、外部服务等集成逻辑。
- 异步任务、并发处理、任务取消、超时及资源释放。
- 错误处理、输入校验、权限控制及安全边界。
- 可能影响现有功能的重构，以及能够通过自动化方式稳定复现的 Bug 修复。

测试应优先覆盖正常流程、异常流程、边界条件和与本次改动相关的回归场景。
无需为每个函数单独创建测试，但必须对**关键行为**提供合理覆盖。

## 3. 文案、样式和布局的验证规则

以下改动**默认不要求**新增自动化测试、自测脚本或测试依赖：

- 静态文案、按钮文字、标题、提示语等纯文本修改。
- 颜色、字体、圆角、阴影、间距等纯样式修改。
- 不涉及业务逻辑的普通组件布局和页面排版调整。
- 图标替换及其他不改变功能行为的视觉调整。

此类改动应根据实际影响进行必要的代码检查、页面预览或**人工视觉验收**，不得为了满足测试要求而创建低价值测试。

出现以下情况时，应**提高**验证力度：

- 修复文字溢出、元素遮挡、错位或窗口尺寸适配问题。
- 修改复杂弹窗、拖拽布局、动态布局或关键页面结构。
- 改动可能影响页面渲染、组件生命周期或已有交互行为。
- 用户明确要求视觉回归测试，或项目已有适用的 UI 自动化测试机制。

优先使用现有预览、截图对比或 UI 测试能力。只有当自动化验证具有**明确价值且能稳定判定结果**时，才新增相应脚本。

## 4. UI 改动中的逻辑例外

如果文案或布局改动**同时涉及功能逻辑**，则必须验证相关行为，不得仅凭页面显示正常就判定通过。

例如：

- 按钮点击、表单提交、输入校验和状态切换。
- 错误提示的触发条件、错误信息映射及异常恢复。
- 多语言切换、动态文案映射和缺失翻译的回退行为。
- 弹窗开关、窗口状态、拖拽交互及快捷键行为。

测试范围应**聚焦于实际修改的逻辑**，不得借机引入与任务无关的大规模测试。

## 5. 桌面系统与外部依赖的验证

涉及窗口管理、系统托盘、全局快捷键、系统权限、模型文件、外部服务或真实引擎时，必须制定与风险相匹配的验证方案。

- 能通过单元测试或集成测试稳定验证的部分，应优先自动化。
- 依赖真实操作系统、桌面环境或硬件行为的部分，应结合实际运行验收。
- 依赖网络、真实模型或外部服务的测试，应明确其**前置条件**；适合使用 Mock 的场景优先使用 Mock。
- **环境限制导致无法完成验证时，必须明确说明未验证的范围及原因**，不得将其标记为通过。

不得为了测试而擅自删除、覆盖用户数据，或执行未经授权的破坏性操作。

## 6. 测试脚本的质量要求

新增自测脚本必须满足：

- 有明确的**用途、运行命令、前置条件和预期结果**。
- 可重复执行，并通过**明确断言**判断成功或失败。
- 不得仅以「脚本正常退出」「进程未崩溃」或「输出包含某个词语」作为充分的通过依据。
- 尽量使用独立测试数据、临时目录和可控依赖，避免污染开发环境或用户数据。
- 优先复用项目现有工具和测试框架，不得引入不必要的依赖或重复实现已有能力。
- 对于**一次性排查脚本**，如果没有持续复用价值，不要求将其永久保留在项目中。

不得为了让测试通过而删除有效断言、跳过关键检查、掩盖实际错误或无故降低测试标准。

> 与本仓现有纪律的衔接：新增 check 必须登记进 `e2e/_check-registry.mjs`（`AGENTS.md` §2 第 13 条）；
> 断言必须可反证（同 §2 第 1 条）；条数写死并由 `check:counts` 与 [`commands.md`](commands.md) 对账。

## 7. 任务完成前的验证要求

完成代码修改后，应根据改动范围执行必要的验证：

- **逻辑改动**：运行相关自动化测试。
- **TypeScript / 前端改动**：根据项目现有工具运行相关类型检查、Lint 或构建检查。
- **Rust 改动**：运行适用的测试、检查或构建命令。
- **跨模块改动**：验证相关接口及关键调用链。
- **视觉改动**：检查实际页面或预览结果；**无需为纯视觉调整强制新增测试脚本**。
- **高风险改动**：执行必要的回归测试及真实环境验收。

不得仅为证明改动正确而无差别运行所有测试。应优先执行与改动**直接相关**的检查；
改动范围较大或影响公共接口时，再扩大验证范围。

## 8. 完成报告

任务完成时，应简要说明：

1. **修改内容及影响范围**。
2. **新增或更新的测试**（如有）。
3. **实际执行的验证命令及结果**。
4. **未执行的必要验证、环境限制和剩余风险**（如有）。

对于不需要新增测试的纯文案或视觉改动，无需刻意编写测试，也无需为了形式完整而罗列无关测试。

---

**最终判断标准**：关键逻辑必须有合理的自动化验证；纯视觉改动以实际界面检查为主；
系统集成按风险组合自动化测试与人工验收；**所有验证结果必须如实报告**。

## 1. 需求一：启动恢复上次播放状态

### 1.1 用户原话 → 可验收条款

| # | 用户原话 | 拆成可验收的条款 |
|---|---|---|
| 1 | 点音乐模块时先判断当前选中的平台与登录状态是否有效 | 进音乐屏时，对**快照里记录的播放平台**做一次登录态校验 |
| 2 | 上次播了音乐才走恢复 | 无快照 → 与现在行为完全一致（不显示播放条） |
| 3 | 本地歌曲：显示播放条 + 定位到时间 + 有歌词，但**暂停** | 三件事都要成立，且 `isPlaying === false` |
| 4 | 非本地歌曲：登录有效则同样显示 | 同上 |
| 5 | 登录失效 → 清掉当前音乐与播放列表（不显示播放条） | 清空后 `queue.length === 0` → 播放条自动隐藏（现成判据） |

### 1.2 现状取证（缺口）

| 需要的东西 | 现状 |
|---|---|
| `queue` / `currentIndex` / `currentSong` / `playUrl` / `progressMs` | **五个全部不持久化**，只在内存 zustand，重启即丢 |
| 播放历史 `miaodock.music.playHistory` | 存的是 `{song, playedAt}[]`（**历史列表**），**不含队列、进度、播放态**，不能当快照用 |
| 登录态 `loginInfo` | **不落 localStorage**，每次启动由 Rust 实时探测（Cookie 在 Rust 侧 `music-cookies.json`） |
| 登录有效性校验 | 已有：网易云 / QQ 是**网络探针**（发请求校验），酷狗 / 咪咕走本地 cookie 解析 |
| 本地歌判定 | `Song._localPath` 存在（或 `provider === 'local'`） |
| 本地歌的重建路径 | 曲库在 `miaodock.music.localSongs`，`loadLocalSongs()` 只填 `localQueue`，**不写 `queue`** |
| 播放条显示条件 | `hidden = queue.length === 0`（现成，恢复后自动显示） |
| 「定位到某时间点但**不播放**」 | ⚠️ **没有现成能力**，详见 §1.4 |

### 1.3 六个必须澄清的边界（**这是本节最重要的部分**）

| # | 问题 | 为什么必须问 | 我的建议 |
|---|---|---|---|
| **Q1** | 登录探针因**网络不通 / 超时**失败，算"登录失效"吗？ | 用户原话是"失效就清掉"。但**"探不动" ≠ "失效"** —— 断网时四个平台全都探不动，若一律清数据，用户一断网就丢播放进度。**这是最容易被忽略的边界** | 区分三态：① 明确未登录（本地 cookie 判定失效）② 探针失败（网络问题）③ 有效。**只有 ① 清数据**；② 保留快照但**本次不自动恢复**（不显示播放条，也不删数据） |
| **Q2** | 恢复时是否**绝对不自动播放**？ | 用户说"暂停播放状态"。确认一次以免歧义（有人会希望"恢复到暂停"但点一下才播） | 按用户原话：**保持暂停**，且不弹任何提示 |
| **Q3** | 队列要**全存**吗？ | 用户可能有 500+ 首的歌单。全量序列化进 localStorage 有容量与启动耗时风险 | 存**当前歌 + 队列**但设上限（如只存当前歌所在的**来源列表**与索引，或队列截断到 N 首）；需用户确认可接受的"恢复后队列不完整"程度 |
| **Q4** | 本地歌曲**文件被移动/删除**了怎么办？ | 恢复时 `convertFileSrc` 仍会生成 URL，但播放失败 | 恢复后做一次**存在性校验**（本地歌可查文件；失败则从队列剔除并**不显示播放条**），避免"看起来在播、点了没反应" |
| **Q5** | 以"当前选中的平台"为准 —— 快照要不要记平台？ | 用户同时登录多平台时，需知道按哪个判定 | 快照记 `provider`；恢复时只校验**那一个**平台的登录态，其余不管 |
| **Q6** | 恢复逻辑跑几次？ | 现在切走音乐屏再切回会**重跑 `init()`**（`init` 无防重入守卫）→ 若把恢复挂在 `init` 里，会**每次进屏都尝试恢复**，且可能覆盖用户当前的操作 | 恢复只在**应用启动**跑一次（放 `main.tsx` 水合处或给 `init` 加"已初始化"守卫），并明确"用户本次已操作过播放器就不再自动恢复" |

### 1.4 ⚠️ 关键技术风险：「定位到时间但不播放」现有机制不支持

现有 `resumeAtMs` 是**为换音质续播设计的**，其消费代码是：

```
if (resumeAtMs > 0) { audio.currentTime = resumeAtMs / 1000; clearResumeAt(); }
if (isPlaying) play(); else pause();
```

表面上"设 `resumeAtMs` + `isPlaying:false`"就能定位而不播放，但有两个真问题：

1. **时序**：`currentTime` 只能在音频 `readyState` 足够时设置。启动恢复是**全新加载**（`src` 刚变），
   此刻设 `currentTime` 会被忽略或抛 `InvalidStateError` —— 表现为**定位没生效、从 0 开始**。
   换音质那条路恰好"能用"，是因为同一首歌的音频**已经加载过**。
   → 需要新增"**等 `loadedmetadata` 后再定位**"的路径，且要能中止（用户中途切歌）。
2. **缺少"恢复中"状态**：从"点进音乐屏"到"定位完成"之间有几百毫秒（网络歌还要解析 URL、可能几秒）。
   这期间播放条怎么显示？**不处理就是"先显示 0:00 再跳一下"**，看起来像 bug。

**结论**：需求 1 不是"把 state 存起来再读回来"那么简单，需要新增：
会话快照持久化 + 恢复状态机（idle → 校验中 → 定位中 → 就绪/放弃）+ 三态登录判定。

### 1.5 影响面

| 层 | 要动的东西 |
|---|---|
| 持久化 | 新增快照键（`Prefs` 之外，建议独立键，别混进 `miaodock.music.prefs`） |
| store | 新增恢复状态机、`restoreSession()`；`init()` 加防重入守卫 |
| Rust | 本地歌存在性校验（若采纳 Q4）；现有 `*_login_status` 已够用，无需新命令 |
| UI | 播放条加入"恢复中"态（避免 0:00 闪跳）；歌词区同理 |
| 断言 | 新增恢复相关断言（快照三态判定、定位在 metadata 之后、断网不清数据） |

## 2. 需求二：全屏补全 + 收起按钮改 `ChevronDown`

### 2.2 ⚠️ 矛盾点：我们的播放器**本来就已经铺满全屏**

两处既有文档口径不一致，必须先定语义：

- `spec-notes.md` **D-44** 拍板：**不照搬参考的 `pageFullscreen`**，理由原话是
  "`.music-exp` 早已是 `position:fixed; inset:0` —— 铺满全屏本来就成立，实际只缺动画"。
- `ui-parity-plan.md` **P2-2** 却写着"要加**进入/退出全屏**"，R2 还给了 portal 方案。
- 并且 `ui-parity-plan.md:35` 把「收起」记成 `ChevronDown` 且标"一致"——
  **但代码实际是 `ChevronLeft`**（文档与代码不一致，本轮顺带发现）。

另外，参考的 `pageFullscreen` **语义不是 OS 全屏**，而是"页面级全屏"：
同一个播放器从 `absolute` 变 `fixed`、`borderRadius: xl→0`、`zIndex` 调整、
**`pt: 48px` 给原生标题栏左上角的"缩小"按钮让位**，并用 `createPortal` 挂到 `body`。

**关键推论**：我们**没有**它那种"页面结构还在、播放器在页面内"的中间态 ——
我们的播放器一出现就盖住一切。所以「进入全屏」在我们的架构下**没有可放大的空间**。

### 2.3 三个选项（需拍板）

| 选项 | 效果 | 与参考一致性 | 成本 | 风险 |
|---|---|---|---|---|
| **A. OS 级窗口全屏**（`window.setFullscreen(true)`） | 点一下**应用窗口真的全屏**（macOS 标题栏/菜单栏隐去），播放器随之铺满物理屏幕 | ✗ 参考没这么做 | 中（需加 Tauri 窗口权限 + 状态同步） | 低；但需确认 macOS 全屏动画与我们的浮层层级是否打架 |
| **B. 内容最大化**（隐藏顶栏/控件，只留封面+歌词） | 播放器内部"更沉浸" | ✗ 参考的 pageFullscreen 不是这个 | 低 | 低；但用户可能觉得"本来就全屏了，这算什么" |
| **C. 不做按钮**，维持 D-44 的结论并**更新文档**（把 P2-2 划掉） | 无变化 | 部分（参考有按钮，我们说明为什么不需要） | 极低 | 低；但用户明确说"遗漏了"，可能不接受 |

**我的倾向：A**。理由：我们的播放器已铺满窗口，唯一还有实际意义的"全屏"就是
**把窗口本身变成全屏** —— 用户能立刻看到差异（窗口变大、标题栏消失），语义也自洽。
但因为它偏离参考做法，**必须由用户拍板**。

**`ChevronDown` 部分无争议**：与参考一致、成本极低、且能让 `ui-parity-plan.md` 里
那句"✓ ChevronDown 一致"从**假的**变成**真的**（现在文档在说谎）。

## 3. 需求三：桌面歌词 icon 问题 + 迁移到灵动岛

### 3.1 icon「显示不完整、hover 才正常」的真因 —— **就是上一轮我自己做的设计**

`.dl-ctrl` 默认 `opacity: 0` + `pointer-events: none`，仅 `.dl-bar:hover` 时才 `opacity: 1`。
也就是说：**控制栏常态是完全不可见的，hover 才淡入**（160ms 过渡，期间半透明+未归位，
这就是用户看到的"显示不完整"）。横向没有被裁切（控制栏约 171px，窗口宽 520px）。

> 我当时的意图是"别让浮层挡住歌词"。但**实际效果与意图相反**：用户看不到入口，
> 以为坏了。**这是设计判断失误，不是 bug。**

**修复方向（低成本）**：改为**常态低透明度可见**（如 `opacity: 0.42`），hover 升到 `1`；
或把"锁定/关闭"两个高频按钮做成常驻、其余 hover 显示。

### 3.2 ⚠️ 迁移可行性：**不能直接迁移**，因为核心能力是架构给的

**桌面歌词的定义就是"浮在所有应用之上"** —— 这是它做成独立窗口的**唯一理由**。

| 能力 | 桌面歌词 | 灵动岛 | 能不能搬 |
|---|---|---|---|
| 歌词行显示（2–5 行） | ✅ | ❌ 无 | ✅ 能加进灵动岛展开态 |
| 播放控制 | ✅ | ✅ | — |
| **跨应用置顶**（浮在任意应用之上） | ✅ 独立窗口 `always_on_top` | ❌ | **❌ 搬不了** |
| **主窗最小化/被遮挡后仍可见** | ✅ | ❌ 主窗内 `fixed` 浮层，随主窗一起消失 | **❌ 搬不了** |
| 屏幕任意拖动 + 位置记忆 | ✅ | ❌ | ❌ 搬不了 |
| 锁定（防误拖） | ✅ | ❌ | ❌ 搬不了 |
| 独立歌词偏好（字号/颜色/行数） | ✅ | ❌ | ✅ 能加 |

**结论**：
- **主窗内的灵动岛永远做不到"跨应用置顶"** —— 这不是实现质量问题，是**进程/窗口架构的硬边界**。
- 所以"把桌面歌词迁移进灵动岛"实质等于 **砍掉「边工作边看歌词」这个场景**（唱 K、跟唱、外语歌看词）。
- 灵动岛能接管的只是"**歌词摘要**"（当前一句），这是**另一个功能**，不是替代。

**同时我要承认用户观察到的真问题**：**两者职责确实重叠了** ——
桌面歌词的控制栏（上一首/播放/下一首/模式/锁定/关闭）与灵动岛展开态（封面/歌名/歌手/进度/播放控制）
在做同一件事的两份 UI。这是**冗余**，应该收敛。

### 3.3 三个方案

| 方案 | 做法 | 得到 | 失去 | 成本 |
|---|---|---|---|---|
| **A. 双轨收敛**（建议） | 桌面歌词**保留**（修 icon 问题）；灵动岛展开态**加"当前一句歌词"**；桌面歌词控制栏**精简**为只留「锁定/关闭」（播放控制交给灵动岛，消除重复 UI） | 两个场景都有；无重复 UI | 无 | 中 |
| **B. 并入灵动岛**（用户设想） | 删歌词窗 + 开关 + 设置项 + 8 个 Rust 命令；歌词只显示在灵动岛展开态 | 少一个开关、一套代码 | **跨应用置顶歌词**（主窗最小化就没了）；`DesktopLyricsSettingsModal` 的 4 项设置也失去载体 | 中高（删除面广） |
| **C. 保留但默认关 + 入口收进灵动岛** | 功能不砍，把"桌面歌词"开关从播放条挪到灵动岛展开态里 | 少一个显眼开关、功能完整 | 无 | 低 |

**我的建议：A**。B 的代价（丢跨应用置顶）与用户的收益预期（少一个开关）**不匹配** ——
用户想要的是"简化"，但 B 实际是"砍功能"。如果用户的目标就是简化，
**C 用更低成本达到同样的"少一个开关"**。

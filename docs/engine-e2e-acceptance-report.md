### 2.1 E1 · 引擎真实启动

**判据**：锁定版本引擎可被拉起；`GET /health` / `/docs` 就绪；日志打印**生效参数快照**。

**做法**：`selftest:app:e11:real` 从**应用 stdout**（不是配置、不是内存变量）读回参数快照。这是与
`launch-plan-check` 完全不同的第二条路径 —— 后者验的是"配方拼得对"，这里验的是"**事情真的这么发生了**"。

**实测**（本轮）：

```
[miao-dock] ③ llm    : …/llama-server -m …/sakura-1.5b-qwen2.5-v1.0-fp16.gguf --port 8080 -c 4096 -ngl 99（由 manga-service 拉起，见《04》§9.1 Tier1）
[miao-dock] ② engine : …/python main.py --host 127.0.0.1 --port 8000 --use-gpu --models-ttl 1800 --nonce None（经 child-watch 看守）
[miao-dock] ② engine.cwd : …/runtimes/manga-translator/src/server
[miao-dock] ① service: node service/src/server.mjs  env=（无）
[miao-dock] ③ LLM 归属 manga-service —— 本进程不 spawn（8080 由它负责）
```

5 行，**≥4 行**的判据满足。第 5 行尤其重要：它把**③ 的归属方**写进了快照，是 S4「归属权移交」的对外凭证。

**③ 预拉起这条路径单独复核过**（手工起 manga-service，real 协议）：

```
[manga-service] 拉起 ③ LLM：…/child-watch.mjs -- …/llama-server -m …/sakura-…-fp16.gguf --port 8080 -c 4096 -ngl 99
[manga-service] ③ LLM 就绪：sakura-1.5b-qwen2.5-v1.0-fp16 @ 8080（pid=79768）   ← 1.8 s

> 🔴 **本项在本轮踩过一个坑**：第一次跑 `e11:real` 时 ③ 在 300 s 内**没起来**，看起来像 S4 的归属权移交坏了。

### 2.4 E4 · 档位切换

**判据**：配置切 Tiny↔Small 后重启，`/health` 的 `sidecar.tier` 与实际加载权重一致。

**这条判据里真正难的不是"切"，是"一致"**：把 `sidecar.tier` 报成"用户配置的那一档"是最省事、也最容易写的实现
—— 它每次都能和设置页的下拉框对上，看起来永远正确；但它会和**事实**分叉：用户配 `small`、机器上只有 Tiny 的权重，
于是界面说"小档"、跑的是 1.5B，质量差异被静静吞掉，而"翻译变差了"这种反馈**根本追溯不到根因**。

**实测 6/0**：

| 断言 | 结果 |
|---|---|
| E4.1 档位→权重表里 Small/Medium **显式声明为 null** | `{"tiny":"sakura-1.5b-…-fp16.gguf","small":null,"medium":null}` |
| E4.2 Small 未声明 ⇒ `resolveLlmLaunch({tier:"small"})` **抛 `TIER_MODEL_UNDECLARED`**（绝不回落 tiny） | 抛错 + `available:["tiny"]` |
| E4.3 real 协议下 `availableTiers()` 恰为 `["tiny"]` | `["tiny"]` |
| E4.4 `/health.sidecar.tier` 报的是**生效档位**（配 `small` ⇒ 夹回 `tiny`） | 配置=small / 上报=`tiny` |
| E4.5 `sidecar.model` == tiny 权重的 **model id**（不得泄露本机绝对路径） | `sakura-1.5b-qwen2.5-v1.0-fp16`（含路径分隔符=false） |
| E4.6 该权重文件在盘上真实存在且落在 `models/sakura/` 下 | 存在=true 目录符合=true |

**反证 4/4**：`tierModelPath` 静默回落 / `/health` 报配置档位 / `modelIdOf` 去掉 basename / `sidecar.model` 编一个权重名 —— 四条各自都让对应断言**实测变红**。

> ⚠️ **本项有明确的未验半边**：`TIER_LLM_MODELS` 目前**只固化了 Tiny**（`small: null` / `medium: null`）。
> ⇒「切到 Small 后 `/health` 显示 small」这件事**本机做不到**（Small 的权重文件名与校验值还没有来源）。
> 脚本因此**反向**取证：配 `small` 必须被**夹回 tiny 且显式**（不能静默）。正面那一半见 §4。
>
> 🔴 **E4.5 照出一个真缺陷**（本轮修掉，见 §3-2）。

**判据**：空闲 5 min → LLM 进程退出、内存下降；再提交任务 → 自动拉起并成功（懒加载恢复）。

实测条件用 `MIAO_IDLE_LLM_MS` 缩短到 2 s（否则用例要跑 5 分钟），**机制本身不变**。

| 断言 | 结果 |
|---|---|
| E6.1 空闲达阈值后 ③ **真的退出**（端口不通，不是"以为退了"） | 端口 8900 已不通 |
| E6.2 §9.4「卸载 ≠ 未就绪」：卸载后服务**仍 running**、`/health` 照常 200 | `health=200 status=ok sidecar=running`，③端口通=false |
| E6.3 留痕：「空闲 … ⇒ 卸载 ③ LLM」 | 空闲 2s ≥ 2s ⇒ 卸载 |

### 2.8 E8 · 加速后端

**判据**：macOS 走 MPS；GPU 启动失败 → 自动回退 CPU 且 `degraded` 上报（**不静默**）。

**这条判据里最容易被写坏的是"不静默"的**反面**：静默地喊狼来了。**
「回退 CPU 就报 degraded」很好写、永远不会漏报；但它会把**用户主动选的 CPU** 一起报成故障
—— 设置页里明明写着「强制 CPU（最慢，但兼容性最好）」，用户点了，界面却弹 `degraded`；
下次真回退时，用户已经学会忽略它了。

规格的依据是 §7.4-3 的措辞：「若指定 GPU 后端**启动失败** → 自动回退 CPU 并…」——
触发条件是「**启动失败**」，不是「没在用 GPU」。两条路径在本版里长得一样（都是 `useGpu === false`），
靠 `choice` 区分。所以脚本**分别起三轮真服务**取证，缺一条都不算验过：

| 断言 | 结果 |
|---|---|
| E8.1 真机硬件探测：darwin/arm64 上 `accel === "mps"` | `platform=darwin arch=arm64 accel=mps` / `gpu={"kind":"metal","unifiedGb":16}` |
| E8.2 对照组：不关 GPU ⇒ `accel=mps` + `/health.status=ok`（degraded **不是**恒报） | `status=ok state=running accel=mps` |
| E8.3 GPU 被关掉（`choice=auto`，即"启动失败后重拉"这条路径）⇒ `accel=cpu` + `state=degraded` + 顶层 `status=degraded` | 三者齐 |
| E8.4 **用户自选 CPU ⇒ 不报 degraded** | `status=ok state=running accel=cpu choice=cpu source=file` |
| E8.5 `/engine/options.accel.effective` 与 `/health.sidecar.accel` **三轮都同值**；两轮 cpu 的 `reason` **文案不同** | 回退=`已回退 CPU（硬件推荐 mps）` / 自选=`用户指定 CPU（非回退）` |
| E8.6 后端候选里**没有**本机不可用的 CUDA（假控件比缺控件更伤） | `[auto,mps,cpu]` |

**反证 4/4**：回退做成静默 / 去掉"用户自选"的区分 / Metal 不认 MPS / 后端候选恒含 CUDA。

> 🔴 **本项有明确的未验半边**：「MPS 启动**真的失败**并触发回退」这一半本机做不到 —— 本机 M4 的 MPS 是好的，
> 人为搞挂需要改引擎/系统层。E8 验的是"**回退发生之后**服务怎么上报"；
> "回退是**谁**触发的"（Rust 侧 `ServiceManager` 的失败检测）见 §4。
>
> 🔴 **E8.4 照出一个真缺陷**（本轮修掉，见 §3-1）。

### 3-1 `resolveAccel` 把"用户自选 CPU"误报成故障（E8.4 照出）

`useGpu === false` 有**两种**来源，外观相同、含义相反：

| 来源 | `choice` | 含义 | 该不该 `degraded` |
|---|---|---|---|
| 用户在设置页选「强制 CPU」 | `'cpu'` | **他主动要的** | ❌ 不该 |
| Rust 侧 GPU 起不来、注入 `MIAO_ENGINE_USE_GPU=0` 重拉 | `'auto'` | 真回退 | ✅ 该 |

原实现把两者合并 ⇒ 用户自选 CPU 时界面报"故障"。规格依据是 §7.4-3 的措辞限定在「**启动失败**」。

**修**：`degraded: !byUserChoice && hardwareAccel !== 'cpu'`，并让 `reason` 文案能区分两者。

### 3-2 `sidecar.model` 泄露本机绝对路径（E4.5 照出）

`modelIdOf()` 有两条取值分支，**形态不一致**：从命令行 `-m` 反解的那条做了 `path.basename`，
而"优先取 `launch.model`"的那条**漏了** —— 真档的 `launch.model` 是**盘上绝对路径**，
于是 `/health.sidecar.model` 把 `…/runtimes/manga-translator/models/sakura/sakura-…-fp16` 整个泄给插件。
契约《03》§5.1 的示例是 **model id**（`sakura-1.5b-qwen2.5-v1.0-iq4xs`），`/engine/status` 的 `llm.model` 同。

**修**：两条分支都 `basename` 去扩展名。修完断言 `E4.5` 才从 ✗ 转 ✓ —— **是修实现，不是放宽断言**。

### 3-3 反证轮把源文件**永久留在被破坏状态**（E4 反证轮照出；`units-structure-check.mjs` 有同一错法）

反证轮的形态是"改坏源码 → 跑 → 断言必须变红 → 还原"。原实现把**还原写在 `try` 之后**。
当某条破坏让服务**启动即崩**（去掉档位夹取 ⇒ `TIER_MODEL_UNDECLARED` 抛在启动路径上），
`runAll()` 抛异常 ⇒ 还原那行**根本不会执行** ⇒ `service/src/server.mjs` 停在被改写的状态，
只能靠 `git checkout` 手工救回（本轮实测踩到）。

**修**：还原一律进 `finally`；异常本身也算"本轮判红"（服务都起不来了，断言自无变绿可能），
但**在输出里明说原因是异常**，不与"断言精准命中"混为一谈。

> 🔴 **同一个错法在另一个脚本里还有一份**（S7 全量门照出）：`e2e/units-structure-check.mjs` 的反证轮
> 还原**已经写在 `finally` 里**，但 `finally` 里**抛异常**同样会掀翻整轮（宿主的删除守卫 / 权限 / 文件被占用都会）。
> 后果比"那条没跑"严重得多：(a) 后面所有改错**一条都不跑**；(b) 源码树留在**被改坏**状态
> ⇒ **下一次正向轮**莫名其妙少一条（实测 `check:units` 37 → 36），而 `check:docs` 只会报
> "文档写 37、脚本实际 36" —— **完全指不到真正的原因**。
> 修法：还原动作包 `try/catch`，**失败只登记、绝不抛**，由已有的「恢复校验」段读盘复核后统一判红，
> 并额外打印"恢复**动作本身**失败"的原因（把"字节不一致"与"根本没删掉"分开）。
>
> ⚠️ 触发它的是**宿主的删除守卫配额**（按**工具调用**记，阈值 50）—— 把整套门塞进一次命令里跑时，
> 反证轮（`check:units:refute` 44 条 / `check:music:refute` 180 条）注定打满。⇒ 反证轮**一条一条单独跑**
> （见 §5-19）。这与"给被测应用摘掉 shim"（§5-15）是**两件事**。

### 3-4 重启后 ③ 被"上一轮的活动"判成空闲并**卸载**（E11 照出）

`store.init()` 会把**上一轮的终态任务**从盘上恢复进 `store.tasks` —— 这是对的（任务清单要显示历史）。
但 `idle-policy.mjs` 的 `lastActivityAt()` 把这些历史任务的 `createdAt` / `finishedAt` 也当成"任务活动"
取最大值，于是重启后的**第一次判定**就是：

```
now − 上一轮的 finishedAt  ≥  5 min   ⇒   卸载 ③ LLM
```

③ 刚被拉起就被下一次 tick 卸掉。**用户看到的是"重启 Box 之后翻译一直起不来"**；
而 `neverRan`（"本次运行还没有跑过任务、没有热态可卸"）这条判据本意正是要挡住它 —— 它被**静默绕过**了
（判据问的是"有没有任务"，而不是"任务属不属于本次运行"）。

**为什么这个缺陷藏得住**：`check:e5e6` 原先用 `mkdtempSync`（**全新空目录**）⇒ 永远不复现；
E11 用仓库内**固定**的 `.tmp-selftest`（注释写着"每次自检从空目录开始"，代码却**从来没清过**）⇒ 稳定复现。
「手工复现不复现、脚本复现」这个差异本身就是线索 —— 于是顺着它去查"两边的状态目录有什么不同"。

**修**（产品侧，`service/src/`）：
- `Store` 新增 `runtimeStartedAtMs`（**毫秒**精度；不复用 `startedAt` —— 那个 `nowIso()` 截掉了毫秒，
  比大小会引入最多 1 s 偏斜）；
- `lastActivityAt(store, since = runtimeStartMs(store))`：**早于本进程启动的活动一律不算** ⇒ 返回 `null`
  ⇒ 落到 `neverRan` ⇒ 不卸。这是保守且正确的结论：本进程没跑过任务，就**没有热态可卸**
  （③ 是刚拉起的冷进程，卸了也省不下什么）；
- 逃生开关 `MIAO_IDLE_SCOPE=all` 恢复旧口径（`since = null`），供反证；
- 假 store（无 `runtimeStartedAtMs`）⇒ 退回旧行为 ⇒ 既有纯函数断言**全部不受影响**。

**修**（测试侧，`e2e/lifespan-selftest.mjs`）：`TMP` 从仓库内固定路径改成 `mkdtempSync`，
让"每次从空目录开始"**名副其实**。
⚠️ 但这条**只是测试卫生**，不是修复 —— 若只改它而不改产品，E11 会变绿而**真实用户重启 Box 后照样踩**。
所以两条都做了，且第 3 件（反证）打在产品侧的行为上。

**三件套**：
- 正向：`check:e5e6` 新增 **E6.7a / E6.7 / E6.8**（共 **16/0**）—— 用**同一 `MIAO_STATE_DIR` 故意重启**服务；
  E6.7 断言"③ 不该被卸"，E6.8 是对照"跑过任务后**仍要**被卸"（防把机制改死）；
- 反证：`MIAO_IDLE_SCOPE=all`（恢复"活动含历史"的旧口径）⇒ **E6.7 变红**（反证 **3/3**）。

### 3-5 `selftest:app` 的 `S2c` **恒红**且长期无人发现（S7 全量门照出）

S4 把 ③ 的归属权移交 manga-service（《04》§9.1）之后，本 Manager 直接持有的子进程从 3 个变成 2 个，
于是断言被改成 `st.children.len() == 2`。**但 `Children::view()` 是「固定三行的视图」** ——
`service / engine / llm` 三项恒出，缺席的那项 `pid = None` ⇒ **长度恒为 3** ⇒ 这条断言**永远为假**。

**为什么藏得住**：S7 只跑 `--e11` 子集（`selftest:app:e11:real`），而 `S2c` 在**默认的 B/S 组**里，
根本没进 S7 的门；而"恒红"与"恒绿"不同 —— 它不会让别的断言变红，只是自己一直红着没人跑。

**修**：改成**按名字点名**，三个错法都堵掉 ——
① 数长度（恒 3）不行；② 只数"`pid` 非空"的个数也不行（① 与 ② 混着数，"少起 ① + 多起 ③"能凑够 2）；
③ 放宽成 `>= 2` 更不行（那正是这条断言要防的"少起了一个进程"）。
所以逐项断言：`service` 与 `engine` 各 `pid = Some` 且 `alive`，并**反向钉住** `llm.pid.is_none()`
（③ 已归 manga-service，是本进程的**孙**进程）。③ 自己的存活由 `/health.sidecar.llm` 那条链路负责
（`check:contract` / `check:engine-settings` / E11），**不在本断言范围内** —— 反过来把它钉住，
哪天 ③ 又被本进程拉起来，会红，而那不是噪音、是**契约变更的信号**。

修完 `selftest:app` **16/16**（原 15/16）。这条本可以"把断言删掉/放宽"糊过去 —— 那正是本项目明令禁止的。

### 3-6 设置页「②翻译服务」自取消守卫被 `StrictMode` 双调用永久置假（S6 取证图照出）

`src/screens/settings/engine-state.ts` 里有一个"组件还在吗"的守卫：卸载时把 `alive.current` 置 `false`，
异步回来后据此丢弃结果。写法是 `useEffect(() => () => { alive.current = false; }, [])` —— **只写了卸载那一半**。

`main.tsx` 开着 `React.StrictMode`，开发模式下 mount 的 effect 会跑两遍：
`effect₁ → cleanup₁（alive=false）→ effect₂`，而 ref 是**同一个对象**，cleanup₁ 之后再没有任何地方把它置回 `true`。
于是两次 `reload()` 的 promise 都撞上 `if (!alive.current) return` ⇒ **数据不落地、错误也不落地**
⇒ 界面**永久停在「读取中…」**。

**为什么它极难归因**：服务端实测 1 ms 就答完了（`/engine/options` 首跑 13 ms、之后 1 ms），
所以症状**看起来像"后端慢 / 还在加载"**；而生产构建没有这次双调用 ⇒ 只在 `npm run dev` 与
**截图取证**（走 vite dev server）里发作 —— 这正是它一直没被人工发现的原因：**是 05 号取证图把它照出来的**。
本仓已有先例可循：`screens/lyrics/index.ts` 就是为了躲开这次双调用而**刻意不套** `StrictMode`。

**修**：挂载时显式 `alive.current = true`（一行，但它才是这个守卫**唯一正确**的写法）。

**三件套**：正向 `ENGINE.hook.strictModeAliveGuard`（`check:settings` 134 → **135**）；
反证 `去掉置位那一半`（`check:settings:refute` 62 → **63**，确认该断言会因此变红）。

| 状态 | 页面上 `<img>` | 通过插件过滤规则（可见 + 渲染 ≥60×60 + 原图 ≥100×100） |
|---|---|---|

先滚到底再唤面板，并把这一步的实测数字记进报告。

## 5. 环境陷阱（本轮实测踩到，写下来免得下次再踩）

1. **两仓的端到端**不能并发**。`miao-trans` 的 `verify.mjs` 把 mock 服务**硬编码在 5180**，
   而 miao-dock 的 manga-service 也在 5180–5190 段；并发时 verify 会连到**真服务**上，
   报 `PERMISSION_DENIED` 并掉到 20/24（**那不是回归，是抢端口**）。串行重跑即 27/27。
2. **E11 `real` 首次失败曾被误判成"内存抢用"**：现象是 ③ 在 300 s 预算内起不来。
   当时归因为"3.3 GB 的 llama-server 与 Chromium 抢内存"，但**真因是 §3-4 的空闲卸载缺陷**（跨轮状态污染）。
   教训：把"**手工能跑通、脚本跑不通**"记成"资源竞争"会让人停在错误方向上 —— 应当先问
   "两个场景的**输入**差在哪"（这里是状态目录是空还是带着上一轮记录），而不是先怀疑资源。
3. **`MIAO_ROOT` 不能是 `/tmp`**：`config.mjs` 的 `validateRoot` 有黑名单（`/tmp` 命中即抛）。
   临时根用 `os.tmpdir()`（macOS 上是 `/var/folders/…`）。
4. **反证轮的破坏必须语法合法**：只替换 `if (...)` 那一行会留下悬空的 `else` ⇒ 模块加载就抛
   `Unexpected token 'else'`，断言"变红"是因为根本没跑起来，**不可归因**。两行一起换。
5. **ESM 按 URL 强缓存**：反证轮改了磁盘上的模块，**父进程的静态 `import` 拿到的仍是旧的那份** ⇒
   断言不可能变红，而它看起来"跑过了"（实测 E7 反证 0/3 假阳性）。
   两条解法都用过：另起子进程问（E4/E10 的 `askChild`）、带 `?v=<mtime:size>` 的动态 `import`（E7）。
6. **本机沙箱会拦"批量删除"**：`fs.rmSync` 被 CLI 的 `safe-delete` shim 包了一层，单轮展开
   **> 50 条目**即抛 `SAFE_DELETE_BULK_CONFIRM_REQUIRED`（实测：递归清空 `.tmp-selftest` 展开 65 条 ⇒ 直接抛错，
   连 trash 路径也过同一道守卫）。⇒ 夹具的临时根一律用 `mkdtempSync`（落在 `os.tmpdir()`）**且不做递归清理**。
   这与"上次失败留下的残留"叠加时尤其气人：想清干净反而起不来。
7. **真实站点测试产物别散在 `e2e/`**：`e2e/` 只放脚本，运行产物（漫画原文/译文、浏览器 profile、
   服务状态、日志）一律落 `miao-trans/.temp-translate-test/e9-<时间戳>/`（已 gitignore）。
   状态目录**每轮全新**很关键 —— 复用同一个 `MIAO_STATE_DIR` 会让 `/tasks` 看到上一轮的任务，
   "只建了一个 Task"这类断言就会莫名其妙地红（E11 那次是反过来：复用状态目录**照出了真缺陷**，见 §3-4）。
8. **`pageerror` 里混着站点自己的异常**：真实站点会抛 `ClError: CBNL`（它的统计/广告脚本，
   不带扩展跑同一页也复现 —— 侦察脚本就是**不带扩展**跑的对照）。所以"无 JS 异常"这条断言
   必须**按来源分流**：`stack/message` 里出现 `chrome-extension://` 的算插件自身，其余单列记录。
   一刀切会把站点噪声算成插件缺陷。
9. **可达性预检别用 HTTP**：该站点对 `HEAD` 直接回 **400**；而用 `GET`（哪怕带 `Range`）
   会被限速到 **45 s 以上**（真实浏览器打开只要 ~2 s）。所以预检只做 **TCP 443**，
   HTTP 层成不成立交给真正的 `page.goto`（并把它的状态码记进报告）。
10. **面板缩略图网格每页 20 格**（`GRID.perPage`）：`thumb-cell` 的 DOM 里**最多只有 20 个**。
    "网格里有 31 个格子"这类断言**永远不可能为真** —— 第 1 页 20 格、第 2 页 11 格。
    这是 E9 上一版真正卡住的地方（报 "等待超时：扫描到 31 张"，看起来像插件扫不到图，其实是断言写错了）。
11. 🔴 **引擎的执行器（`:8001`）是"孙进程"，只杀直接子进程会漏掉它** —— 漏掉的后果**极具欺骗性**：
    下一轮引擎照样 `running`（uvicorn 起得来），HTTP 层面**全是 200 OK**，但真正干活的是
    **上一轮遗留的陈旧执行器**，于是**每一张都** `engine_engine_error`、磁盘上 0 份译文
    （实测：18 张全失败，而日志里唯一的线索是一行
    `ERROR: [Errno 48] error while attempting to bind on address ('127.0.0.1', 8001): address already in use`）。
    ⇒ 夹具脚本的**前置端口检查**与**收尾清理**都必须把 `8001` 一起算上；E9 额外加了一道守卫：
    引擎就绪后立刻在它的日志里 grep `Errno 48`，命中就当场报"端口被上一轮占着"，**不让它伪装成引擎故障**。
    同一事实在 E11 那边是"三进程树回收"要验的东西（执行器也是孙进程），两个脚本各管一遍。
12. **勾选缩略图要点"格子里的勾选框"，不是格子本身**：`ThumbCell` 的七层结构里 L0–L4 一律
    `pointer-events: none`（免得整格选中蒙层吞掉指针事件），唯一接管点击的是
    `button.mt-thumb__checkbox`。点容器**不报错、只是没反应** ——
    症状是 `已选 0 张`，接着提交按钮一直 disabled（实测踩到）。
13. **`/tasks` 的主键是 `taskId`，不是 `id`**（`store.listView()` / `detailView()` 一致）。
    写成 `.id` 会拼出 `/api/v1/tasks/undefined` ⇒ 404 ⇒ 「等 items 到齐」永远等不到，
    超时后报 `items=0 status=undefined` —— **看着像任务没跑，其实任务早就跑完了、磁盘上译文都在**。
14. 🔴 **面板有"假就绪"（乐观渲染 → 异步翻回），断言必须"等状态稳定"，不能"等元素出现"**：
    面板挂载时**先渲染成 `idle`**（此刻选择工具条与计数器**已经可见**），紧接着**异步**的
    「恢复进行中任务」（`ACTIVE_TASK_GET` → `TASK_REFRESH`）把它推回 `done` ⇒
    漫画名输入框变 `readOnly`（`caps.comicName` 只对 `idle` 为真）。
    症状**辨识度极高但归因极易错**：日志里明明写着 `state=idle`，报错却是
    `locator.fill: element is not editable` / 提交按钮 `disabled`。
    ⇒ 正确做法是轮询 `data-state` 并**要求连续 4–5 次采样不变**才动作，动作完**再复验一次**
    （异步恢复的到达时刻不保证；它若在填完名字之后才落地，会把状态翻回去并**清空刚做的选择**）。
    ⚠️ 「轮询一个值直到它等于期望值」是**错的方向** —— 竞态的定义就是"它会变回去"。
15. 🔴 **WorkBuddy CLI 的 `safe-delete` shim 会经 `NODE_OPTIONS` 注入到"被测应用"里**，
    而它的配额是**按工具调用**记的（阈值 50）。manga-service 建单前要做可写性探测
    （`server.mjs:151 assertRootWritable`：写 `out/.write-probe-*` 再 `unlinkSync`），
    配额一满，**应用删自己刚写的探针文件**也被拦：
    ```
    Error: [safe-delete][SAFE_DELETE_BULK_CONFIRM_REQUIRED] {"count":50,"threshold":50,"scope":"turn"}
        at Object.unlinkSync (node-safe-delete-shim.cjs:665)
        at assertRootWritable (service/src/server.mjs:155)
    ```
    ⇒ 建单 **500**，而磁盘、权限、引擎**全都好好的**；现象是"脚本跑到提交就没下文、静默 15 分钟"。
    识别方法：看**完整栈**里有没有一个**应用从没 import 过**的模块（`…/vendor/shim/…`）。
    E9 的做法是给被测应用一份**干净环境**（摘掉 `NODE_OPTIONS` 里的那条 `--require` 与
    `CODEBUDDY_SAFE_DELETE_*` / `CODEBUDDY_TOOL_CALL_ID`，**保留其余 `NODE_OPTIONS`**），
    并 spawn 一个最小子进程自检 `fs.unlinkSync` 是否已恢复原生（打印 `CLEAN` 才放行）。
    ⚠️ 这不是"绕过安全检查"，而是**别把测试环境装进被测应用** —— 生产里 Box 由 Tauri 直接 spawn，
    根本没有这层 shim。另外给建单加了"**90 s 内必须出现任务**"的快速失败 + 打印服务端日志尾巴。
16. 🔴 **本插件的契约是「一次提交 = 一个任务」**，判据 E9 要的是「同一队列、同一落盘规则、序号连续」，
    **不是**"一个 Task 两个 Batch"（那是 E3 的判据）。证据链：
    · 插件 `onRetryFailed` 的注释：「作为**新任务**提交（comicName 复用 → 服务端续编号）」；
    · 服务端 `createTask` 只按 `idempotencyKey` 去重，**从不按漫画名归并**；
    · 「前 20 → `POST /tasks`，其余 → `appendBatch` 到同一任务」只发生在**同一次提交内部**
      （`splitIntoBatches`：「不产生新任务」），而面板单次上限就是 20（`decideSubmit` 超限即拦截）
      ⇒ 该 append 分支**从 UI 不可达**（登记在 §4 U10）。
    把 E3 的形状（一个 Task）搬到 E9，会让 `tasks.length !== 1` **恒真不成立**、任务明细**恒空**，
    于是空等到 15 min 超时 —— 而磁盘上译文一对不缺。
    ⇒ 跨两次提交，正确断言是：**任务数 = 2、各 1 个 Batch、seq 跨任务首尾相接 1–31**。
17. **`/tasks/{id}` 的 batch 记录里没有 `startedAt/finishedAt`**（只有
    `batchIndex/count/seqFrom/seqTo/status/items`）⇒ 后验阶段拿不到"批次起止"，
    想验「同一队列（串行）」只能找**其它对并发敏感的观测面**。E9 用的是**译文落盘时间的单调性**：
    两个批次若并行执行，019–031 的写入时刻就会与 001–018 交错；串行则必然严格递增。
18. **引擎/LLM 的 stdout 是块缓冲的**（引擎是 Python、非 `-u` 启动）⇒ 卡住时日志可能**滞后若干 KB**，
    "日志停在某一行"不能直接当成"它停在那里"的充分证据。要判定"卡死"还是"只是慢"，
    应当**当面取进程 CPU%**：`ps -o pid=,pcpu=,pmem=,etime=,comm=` —— CPU 恒 0% 是真卡死，
    CPU 高只是慢（大图 + MPS）。E9 的长等待因此加了**心跳 + 进程快照**：
    超过 45 s 每 45 s 打一行进度，超过 120 s 附一次 `ps`（否则一次卡顿就是**静默空等 14 分钟**）。
19. 🔴 **不要把整套门塞进"一次工具调用"里跑**：宿主的删除守卫配额是**按工具调用**记的（阈值 50），
    而反证轮（`check:units:refute` 44 条 / `check:music:refute` 180 条）每条都要改文件再还原，
    删除次数远超 50 ⇒ 会**中途崩**在 `unlinkSync` 上。
    崩的后果比"那条没跑"严重得多：还原没做完 ⇒ **源码树留在被改坏的状态** ⇒
    **下一次正向轮**莫名其妙少一条（`check:units` 37 → 36），而 `check:docs` 只会报
    "文档写 37、脚本实际 36" —— **完全指不到真正的原因**。
    ⇒ 反证轮**一条一条单独跑**；跑之前先确认上一次没留残留（`git status` 看有没有 `??` 的新文件）。
    ⚠️ 这与 §5-15（给**被测应用**摘掉这层 shim）是**两件事**，别混为一谈。
